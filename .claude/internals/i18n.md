# Translations

### The editor's own language (`src/i18n/`, `scripts/i18n.mjs`)

- **Shape.** No library. `i18n/index.ts` is the whole runtime: `t(text, params)` with the English
  text as the key, `tc(context, text)` for a word meant two ways (key `context\u0004text`, gettext's
  separator), `msg(text)` as an identity marker for strings kept in a table and `translate(value)` to
  show one of those (a different name so the extractor does not expect a literal), `format` for the
  ICU subset (`{name}`, `{n, plural, =0 {…} one {# …} other {…}}`, `{x, select, …}`, nesting one level
  through `matchBrace`/`parseBranches`), `josa` for Korean particles (`{name|을}` → 을/를 by the last
  syllable's final jamo; 으로/로 also treats ㄹ as open), `placeholderNames` (what a translation must
  keep), `makeTranslator` (a `t` over a catalogue of someone else's — the plugin API). The locale is a
  module variable (`setLocale` / `locale` / `onLocaleChange`) because `validate.ts` and `save.ts`
  build messages with no store in reach; `i18n/react.ts#useT` is `useSyncExternalStore` over it so a
  component re-renders on change. Catalogues are `src/i18n/<locale>.json`, flat, imported statically
  (`resolveJsonModule` was turned on for it); `ko.json` is the only one. Lazy-loading a catalogue is
  the obvious next step when one grows past a few KB — nothing depends on them being synchronous
  except the first render.
- **Where the locale comes from.** `Preferences.language` (`"auto" | Locale`, default `"auto"`);
  `localeAtom` (`preferencesAtoms.ts`) resolves it against `navigator.language`; `useApplyPreferences`
  calls `setLocale` at startup and on every change, and sets `document.documentElement.lang` (fonts
  and hyphenation follow it). The Korean faces sit *after* the Latin ones in `--font-ui` so Latin text
  keeps Inter and only Hangul falls through. `useHotkeys` ignores `isComposing` / keyCode 229 — a
  Hangul syllable is several keystrokes and the single-letter hotkeys fired mid-composition.
- **Why English-as-key, and why a homegrown `t`.** Ids (`menu.file.open`) let the English change
  under a stale Korean; with the text as the key an edit orphans the translation, which the script
  reports. Lingui does the same thing with PO files and a babel/SWC macro; that is a second
  toolchain in a Vite + oxlint + tsc build for what is ~200 lines here, and the typescript package is
  already a dependency for the extractor. Korean has no plural forms, so plural machinery matters
  less than the particle rule, which no library does.
- **Enforcement.** `scripts/lib/i18n.mjs#extractMessages` walks `src/` with the TypeScript compiler
  (only files that import an `i18n` module are read — `t` is a common local name elsewhere), records
  `t`/`tc`/`msg` calls, errors on a non-literal argument. `checkCatalogue` → missing / unused /
  mismatched (placeholder sets differ) / untranslated (empty; allowed, shows English).
  `npm run i18n` reports and exits non-zero on the first three; `--write` rewrites each catalogue with
  the source's key set in source order. `tests/i18n.test.ts` runs the same check over the real tree,
  so the catalogues cannot drift; an empty value is the one thing it lets through, by decision — a
  string can land before its Korean does. Tightening that to "every key translated" is one line.
- **Plugins.** `api.i18n` (`host.ts`): `register(catalogues)` merges per language (later over
  earlier, the `Disposable` removes), `t` / `tc` from `makeTranslator` over the merged map,
  `language`, and the `"language"` event (`EVENT_ATOMS.language = [localeAtom]`). The plugin ships
  its catalogues inside its bundle; nothing is fetched. No plugin uses it yet. The shared plugin CI
  in `scm-js/.github` is where a plugin-side `i18n` check would go.
- **Menus and other named tables.** `MenuBar.tsx`'s `Item.label` is the English name *and* the
  identity: `withPluginItems` matches `MenuPath` segments and `after` against it, so it is never
  translated in the model — built-in labels are `msg("…")`, the renderer (`Items`, the triggers)
  shows `translate(label)`, and a plugin's label passes through untouched (no catalogue entry).
  Labels built at run time (`Undo {what}`, a recent file) are `t()`'d where built and go through
  `translate` a second time harmlessly. `LAYERS` (same file) is the one place the layer names
  live — `LayersPanel`, `ToolBar`, `StatusBar`, `Docks` all `translate(LAYERS…label)`. The same
  shape works for any table of named things (`TEXT_ENCODINGS`, `VERSION_LABEL`). Decided against
  separate ids: the English label already is one, and no plugin breaks.
- **What is not done.** The chrome (menus, toolbar, status bar, tabs, layers panel, dialog frame
  buttons) and the Map Revision dialog are through `t()`; the other dialogs and panels — most of
  the ~1000 literals across 44 component files (`grep -rhoE '>[A-Z][^<>{}]{3,}<' src/components`
  is a rough count) — remain. Undo/redo *labels* (`history.ts`'s "Paint terrain" etc.) and
  status messages from the hooks are still English inside a translated frame. The trigger definition names and StarEdit's unit names are format vocabulary
  (text triggers, the plugin API) and must stay English; display names are a separate lookup still
  to build. `localeCompare` (5 sites) should become one `Intl.Collator(locale)`. Docs in Korean would
  be a `docs/ko/` tree, the screenshot script re-run, and `tests/docs.test.ts` extended — last, since
  it is the part that keeps costing. The Korean in `ko.json` was written by Claude, not a native
  speaker: have it reviewed before it is called done.
